# Вхід за поштою: стан та підключення

## Поточний стан

Інтеграція підготовлена й перевірена локально. Вона **вимкнена**, доки не налаштовані реальний Supabase-проєкт і надсилання листів. Контрольовані відповіді в E2E не є доказом реальної доставки. Чинний вхід через ChatGPT та власник `/admin` збережені. Не вмикайте прапорець лише заради показу нової кнопки.

Це етап входу й серверного Premium. Перенесення показників у хмару та сімейний доступ не входять до цієї зміни; калькулятор продовжує використовувати localStorage.

## 1. Supabase

Використайте окремий проєкт для «КомуналОчки» в акаунті власника. Для налаштування з чату встановіть плагін Supabase та авторизуйте свій акаунт. Не надсилайте паролі або приватні ключі в чат.

Потрібні такі параметри:

- Email provider: увімкнений; нові користувачі можуть реєструватися.
- OTP: **6 цифр**, строк дії **600 секунд**; повторний лист не частіше ніж раз на 60 секунд.
- Site URL: `https://komunalochka.com`.
- Шаблони **Magic Link** та **Confirm Signup**: український код із `emails/login-code.html`; тема «Ваш код для входу в КомуналОчку». Обидва шаблони мають містити `{{ .Token }}`. Текст про 10 хвилин повинен відповідати налаштуванню сервера.
- Не використовуйте тестовий автоматичний вхід чи автоматичне підтвердження пошти.

Логін відбувається кодом, а не посиланням; зарезервовані маршрути Sites `/callback`, `/signin-with-chatgpt`, `/signout-with-chatgpt` залишаються вбудованими.

## 2. Доставка листів

Потрібен виробничий SMTP-провайдер у налаштуваннях Supabase (наприклад, Resend, Brevo або інший наявний сервіс). Стандартний SMTP Supabase призначений для тестів: надсилає лише учасникам команди проєкту та має обмеження кількості листів. Він не підходить для входу всіх відвідувачів.

Налаштуйте перевірений домен відправника й SPF/DKIM за точними записами поштового провайдера. Не замінюйте DNS сайту навмання. Задайте ім’я відправника «КомуналОчка»; адресу виберіть на підтвердженому домені. SMTP-пароль зберігається в Supabase, не у вебклієнті й не в Git. Платні плани не підключаються без погодженого бюджету.

Обмеження OTP і кількості листів налаштовуються на стороні Supabase. Локальний зворотний відлік — лише підказка користувачу, не захист від зловживань. Перед публічним запуском перевірте очікуване навантаження та ліміти перевірки токенів `/auth/v1/user`: серверні запити до провайдера можуть розділяти зовнішню IP-адресу. За потреби перейдіть на рекомендовану провайдером перевірку асиметричних JWT із перевіркою статусу сесії для чутливих операцій.

## 3. Runtime налаштування Sites

Через Sites environment variables додайте:

```text
SUPABASE_URL=https://<реальний-project-ref>.supabase.co
SUPABASE_PUBLISHABLE_KEY=sb_publishable_<публічний-ключ>
EMAIL_LOGIN_ENABLED=true
```

Застосунок приймає саме сучасний **publishable key**. `sb_secret_...`, service role і SMTP-пароль не потрібні й не повинні потрапляти до браузера. Не змінюйте `PREMIUM_ADMIN_EMAIL`, існуючі origins чи прив’язку D1. Після налаштування змінних опублікуйте збережену версію, щоб застосувати нову ревізію середовища.

Конфігурація `GET /api/account/config` віддає лише публічні параметри. Якщо прапорець вимкнений або параметри неповні/некоректні, повертає `{ "enabled": false }`, а чинний вхід залишається доступним.

## 4. Перевірка перед ввімкненням для всіх

На адресі, яку власник явно дозволив використати для тестового листа, перевірте: перший вхід, повторний вхід, неправильний і прострочений код, повторний лист та його фактичне надходження, вихід і відновлення сесії. Потрібна також перевірка доставки на незалежну адресу поза командою Supabase. Не заявляйте про готову доставку на основі самого HTTP-успіху або mock-тесту.

Рекомендується спершу перевірити на окремому тестовому середовищі. Для повернення до попереднього входу задайте `EMAIL_LOGIN_ENABLED=false` й повторно застосуйте розгортання.

## Розмежування акаунтів

- Supabase SDK керує отриманням/оновленням токенів у власному ключі `komunalochka.email-auth.v1`.
- Сервер сам перевіряє bearer-токен через Auth API налаштованого проєкту. Непідтверджений email або недоступний провайдер не дає прав.
- Ідентифікатор `email:<uuid>` не збігається з ідентифікатором Sites. Права двох акаунтів з однаковою поштою автоматично не об’єднуються.
- Email-акаунт не отримує адміністративні права через збіг адреси з власником. `/admin` залишається за вбудованим входом власника Sites. Для старого Premium збережено попередній спосіб входу.
- Показники та журнали калькулятора не передаються провайдеру авторизації й не змінюються при вході. На спільному браузері це все ще локальні дані, а не ізольоване серверне сховище кожного користувача.

## Відтворення перевірок

```sh
npm test
npx tsc --noEmit
# Локальний dev-сервер на 127.0.0.1:4173 має працювати:
BROWSER_CHANNEL=chrome npm run test:email
npm run build
```

`tests/email-browser.cjs` використовує справжній Supabase SDK з контрольованими HTTP-відповідями. Реальних OTP, користувачів чи листів він не створює. `tests/email-auth.test.mjs` перевіряє серверне розмежування та відмову в доступі за некоректних відповідей провайдера.

Офіційні джерела: [Email OTP](https://supabase.com/docs/guides/auth/auth-email-passwordless), [SMTP](https://supabase.com/docs/guides/auth/auth-smtp), [серверна перевірка getUser](https://supabase.com/docs/reference/javascript/auth-getuser), [rate limits](https://supabase.com/docs/guides/auth/rate-limits).
